# Q1: Address to tax lot and buildings

**Fixture status:** Examples are provisional until verified against the selected frozen snapshot, pinned BOR release, or versioned retrieval cache, as applicable. Existing local checks retain their stated query dates; they are not a frozen acceptance baseline. See [expected-answer policy](../roadmap.md#expected-answer-policy).

## Question

> Which tax lot (BBL) and building(s) (BIN) does this street address resolve to, is the match unambiguous, and what characteristics do the records give (year built, building class, residential units, assessed value)?

"BBL" is the NYC tax lot identifier. "BIN" is the NYC building identifier.

### Sub-questions

Tests and ontology fragments reference these IDs. Q1 keeps its ID and passes when all four pass.

| ID | Sub-question | Answer requirements covered |
| --- | --- | --- |
| Q1.1 | Which tax lot does this address resolve to? | 1 (input), 2 (tax lot) |
| Q1.2 | Which buildings are recorded for this tax lot? | 2 (every building, addressed one distinguished), 4 (counts) |
| Q1.3 | Is the address match exact, a variant, ambiguous or not found? | 1 (outcome), 5 (uncertainty); see [Address resolution outcomes](#address-resolution-outcomes) |
| Q1.4 | What are the year built, building class, residential units and assessed value of this tax lot? | 3 (characteristics), 4 (counts) |

## Who asks and why

Every organizer starts from an address. A lot with several buildings changes the unit count they should expect.

## Required content of an answer

1. The input address and the **resolution outcome**: matched exactly, matched by a variant, ambiguous, or not found.
2. The **tax lot** (BBL) it resolves to, and **every building** (BIN) recorded for that lot, not only the one typed. The addressed building is distinguished from the others.
3. **Source-reported characteristics**: year built, building class, residential units, assessed value, each tied to its source record and snapshot.
4. **Counts** for parcels, buildings and residential units, reported **separately**, each with its counting unit named.
5. **Match uncertainty**. Ambiguous matches return distinguishable candidates and never silently select one.

## Caveats the answer must carry

- Say whether the address matched exactly or by a variant.
- A lot is not necessarily one building, so building counts and lot counts differ.
- Residential units are **lot-wide**. A lot-wide unit count must not be copied to each building or summed across its BINs.
- **Two building counts, never one.** `plutoNumBuildings` is PLUTO's count; `buildingsListed` is the number of BINs HPD lists. They differ on about 27% of lots (queried 2026-11-12: 32,847 unregistered lots have no listed buildings, 23,839 registered lots list fewer than PLUTO counts, 831 list more). The answer gives both, each labelled by source, and never presents either as "the number of buildings" on its own.
- **BINs come only from HPD registrations.** A lot with no registration (for example anchor F) resolves to a BBL with no BIN. The answer reports "no building recorded in the HPD registrations", not "no buildings". The building list is complete only for registered buildings.

## Generic example (placeholder values)

`123 Example St, Brooklyn` resolves to BBL `3012340056`, one BIN, built 1931, class C1, 24 units; or to one lot with three BINs.

## Address resolution outcomes

Geosupport decides the outcome. The test classifies a cached response with these rules. Base logic on the return code (GRC) and reason code, never on message text.

| Outcome | Rule applied to the cached response |
| --- | --- |
| `exact` | GRC `00`, a BBL is returned, and the returned house number and street equal the input after case and whitespace normalization only |
| `variant` | A BBL is returned with GRC `00` or `01`, and either the returned address differs from the input beyond case and whitespace (alias, ordinal form, inserted hyphen) or the GRC is `01` (a warning). The answer reports the returned address and the reason code |
| `ambiguous` | GRC `EE` (similar street names). No BBL is chosen. The candidates in the "List of Street Names" field are returned as distinguishable candidates |
| `not_found` | Any other reject GRC, or GRC `00`/`01` with no BBL. The answer reports the GRC, reason code and variants tried, and does not guess a nearby lot |

- Function 1B returns two result sets (1E and 1A). Record both. Read the BBL from the 1A set. If the 1A set has no BBL (for example, address not in PAD), the outcome is `not_found` even when the 1E set succeeded.
- `exact` versus `variant` cannot be told from the GRC alone, because an alias can return GRC `00`. The comparison of input to returned address decides it.
- **Verified against recorded responses (Geosupport 25b, `tests/q1_3/recorded.json`):** GRC `00` success; `EE` street not recognized (similar names in "List of Street Names", possibly none or wrong ones); `11` not recognized with no similar names; `42` house number out of range; `13` no house number. A `00` with an empty BBL means no tax lot (`not_found`). `01` has not been observed yet. A street Geosupport accepts unchanged (`SEVENTH AVENUE`) is `exact`; `54TH STREET`, `54 ST` and `100 BROAD` (returned as `BROAD STREET`) are `variant`.
- A service outage is `unavailable`, never `not_found`.
- **Condominiums:** Geosupport returns the billing BBL. The answer also lists other graph lots that share the returned BIN (`relatedLots`). A unit lot with no shared BIN (for example `1005560059` for 76 Third Avenue) is not found this way.

## Scenarios

- **Address not found, alternate address.** The address is absent from the lot data but the lot appears under an alternate address, a street-name variant or a corner address. The answer reports the match it used and the alternate address, and says the resolution is **inferred**.
- **No match at all.** Reported as "no lot found" with the variants tried. The agent does not guess a nearby lot.

**Pending**: a corner or alternate-address case for the "address not found" scenario. No example exists yet.

## Local snapshot check (queried 2026-11-10, database `justfixwow`)

Values read from `pluto_latest` (26v1) and `hpd_registrations`. These agree with the detail file's anchor properties. They are candidate expected values until a snapshot is frozen.

| Anchor | Address (PLUTO) | BBL | BINs (HPD registrations) | Class | Residential units | Year built | Assessed value (whole dollars, `assesstot`) | PLUTO `numbldgs` |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| D | 224 54 STREET | `3008210012` | `3324448`, `3324450`, `3324451` | C1 | 18 | 1911 | 814,500 | 3 |
| A | 5413 7 AVENUE | `3008260002` | `3014788` | C1 | 32 | 1911 | 868,950 | 1 |

Observations that matter for the model:

- PLUTO holds **one address per lot**. Lot D carries only "224 54 STREET", so the addresses 218 and 220 reach the lot only through a building-level source.
- PLUTO's building count (`numbldgs`) agrees with the number of distinct BINs found for both anchors.
- **Street names are spelled differently across sources.** PLUTO says `5413 7 AVENUE`; HPD says `SEVENTH AVENUE`. PLUTO says `54 STREET`; HPD says `54TH STREET`; HPD also has `52ND STREET` for PLUTO's `52 STREET`. Exact string matching would miss these, so "matched by variant" is a common case, not a rare one.
- PLUTO has no BIN column. Building identifiers come from another source.
- Assessed value is stored in whole dollars. The accepted decision stores money as exact integer cents, so the physical value would be 81,450,000 (D) and 86,895,000 (A). The conversion belongs to the physical mapping.
