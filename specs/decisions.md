# Accepted decisions

A lightweight log of accepted project and modeling choices. Add the date, decision, and a short rationale when a new choice is accepted. Git retains the editing history; separate decision records and approval tooling are not required for the POC.

| Date | Decision | Rationale |
| --- | --- | --- |
| 2026-11-11 | Separate graph, retrieval/extraction, and investigation acceptance. WatchlineOP delivers the graph, mappings, and acceptance fixtures/contracts; the research agent is a downstream consumer. | A validated graph does not establish that document extraction or a complete investigation works. |
| 2026-11-11 | Use a frozen JustFix/WoW snapshot as the sole authority for database-backed test inputs and expected answers. Keep BOR releases and retrieval caches separately identified. | Tests should be reproducible and must not compare snapshot-backed answers against changing live records. |
| 2026-11-11 | Keep question IDs and concept IRIs stable; track semantic artifacts and tests in Git; use this decision log and one identified source snapshot. Rebuild the POC graph and rerun existing tests after accepted model changes. | Keep iteration reproducible with minimal overhead. Formal versioning, migrations, and release governance wait until the POC is viable. |
| 2026-11-11 | Use separate namespaces and identifiers for SKOS concepts, ontology classes/properties, and instances. Record concept-to-element traceability in a compact table; reuse SKOS IRIs directly only where explicitly modeled as controlled values. | Controlled meanings, formal modeling elements, and real-world instances have different roles. Explicit mappings preserve traceability without automatic class/property conversion or additional POC machinery. |
| 2026-11-11 | Prefer shallow, justified taxonomies without a fixed depth. Allow multiple parents and overlapping siblings; justify disjointness separately. Review label ambiguity and disconnected concepts in context rather than prohibit all shared labels or force artificial links. | Keep the vocabulary faithful to the questions and source meanings instead of shaping it to arbitrary structural rules or validator warnings. |
| 2026-11-11 | Make physical source mappings and Neo4j schema explicit, and require source-value reconciliation plus complete validation. Pin the exercised toolchain; use bounded checks and POC rebuilds. | Ontology meaning and shape compilation alone do not specify safe ingestion, physical encodings, identity integrity, or correct persisted answers. A small implementation contract provides these without a release framework. |
| 2026-11-11 | Use repository-relative links for internal documents and public URLs plus dependency notes for external references and producers. | The standalone specification must not depend on a personal filesystem layout or an undeclared sibling checkout. |
| 2026-11-11 | Freeze the Q1 evidence baseline on PLUTO release 26v1 (`pluto_latest`) and HPD registrations as of 2026-05-29 (`hpd_registrations`). Dump identifier and checksum: **pending, to be recorded in `data/README.md`.** | Q1 needs a fixed input and expected-answer authority before any graph test runs. Other sources (ACRIS, DOS, violations, etc.) are frozen when the questions that use them are started. |
| 2026-11-11 | BINs come only from HPD registrations. Q1 accepts that a lot with no HPD registration has no BIN in the graph. | PLUTO has no BIN column, and HPD registrations are the only BIN source in the frozen baseline. Completeness is limited to registered buildings, and the answer must say so. |
| 2026-11-11 | Address variant matching and resolution outcome (exact, variant, ambiguous, not found) are Geosupport's job, not the graph's. The graph stores the resolved BBL and the cached Geosupport response as evidence. | Geosupport is the authority for NYC address normalization. Reimplementing it in the graph would duplicate it and drift from it. |
| 2026-11-11 | Stage 1 keeps a SKOS controlled vocabulary (`vocabulary/watchline.ttl`), built per question from only the terms that enter the graph (node, property or relationship). It is the single source of definitions: schema node and property descriptions are generated from concept definitions and scope notes, not written separately. Revisit after Stages 2 to 6 are redone for Q1, if nothing but the descriptions uses the vocabulary. | Definitions carry the caveats the agent needs (for example lot-wide units, 0 means PLUTO records none) and synonyms map user wording to one term. One source prevents drift between vocabulary and schema. |
| 2026-11-11 | Stage 1 setup. Namespace bases: concepts `https://watchline.example/vocab/`, ontology elements `https://watchline.example/onto/`, instances `https://watchline.example/id/`. Readable concept IDs (kebab-case labels), stable once minted. Layout: `vocabulary/watchline.ttl`, `vocabulary/term-trace.md`, one `tests/qN_M/` folder per sub-question. Q1 vocabulary: 16 concepts in `watchline` plus 5 outcome values in `address-resolution-outcomes`. `related` links are written in both directions. | Readable IDs make the files reviewable; stable IDs keep traces and tests valid. |
| 2026-11-12 | Stage 2 setup. Layout: `profiles/<source_key>.yaml` per source (facts about the source only) and `profiles/qNN.yaml` per question (graph elements, answer fields, diagnostics, terms not stored). No separate crosswalk file: each graph element already names its concept, source column and proving test. Per-record evidence fields are defined only when a question first stores derived edges, claims, documents or cached responses; database facts carry dataset-level provenance. Field names `snake_case` in profiles; graph names exactly as loaded. `scripts/check_profiles.py` (`make profiles`, part of `make graph`) checks files, vocabulary, `data/sources.yaml` and the live graph, and fails on any undeclared label, relationship type or property. | Keeps the schema small and checkable, and stops undeclared elements from entering the graph. |
| 2026-11-12 | Q1 answer contract. Q1.2 reports `buildingsListed` (BINs HPD lists) and `plutoNumBuildings` (PLUTO's count) separately, each with its counting unit. Q1.3 returns `outcome` (matched exactly, matched by variant, ambiguous, not found, service unavailable), `bbl`, `bin`, `inGraph`, `relatedLots`, `candidates`, `grc` and `inferred`; `message` and `tried` are diagnostics kept in logs and tests. | The answer states both building counts rather than reconciling them, and carries the caveats the agent must repeat. |
| 2026-11-12 | Q1 taxonomy: no hierarchy needed. All 21 concepts stay flat; the four Q1.4 characteristics are not grouped in a collection because no schema, graph or answer field uses the set as a unit. `scripts/check_taxonomy.py` and `make taxonomy` are added when the first question has a link or collection to check. Hierarchy lives in the vocabulary only; the graph stores none. Notes in `vocabulary/taxonomy-notes.md`. | A hierarchy exists only where an answer needs it. Adding structure with no consumer would only create something to maintain. |
| 2026-11-12 | Q1 thesaurus: 8 related pairs, written in both directions, each with a kind and justification in `vocabulary/thesaurus-notes.md`. A related link must connect concepts the schema does not already connect, so 11 property-of and relationship-endpoint links were dropped; the identifier links (`bbl`/`tax-lot`, `bin`/`building`) were kept by choice. Label review: `number of buildings` removed as an alternative label of `pluto-building-count`; hidden labels added for PLUTO column spellings. External mappings: none sought for Q1; revisit when party, organization or provenance questions arrive. `scripts/check_thesaurus.py` and `make thesaurus` added. | The thesaurus adds navigation the schema lacks and does not restate it. Building counts must always be given as two labelled numbers. |
| 2026-11-12 | Q1 graph model: `Lot` (BBL key) and `Building` (BIN key) joined by `HAS_BUILDING`. Scope is HPD-registered lots plus unregistered PLUTO lots with 3 or more residential units. BINs come only from valid HPD registrations. When the most recent registrations disagree on an address, the address is absent. PLUTO year 0 and blank class are absent; units and assessed value of 0 are kept as "PLUTO records none". Provenance is dataset-level only, with no per-record source nodes. | Smallest graph that answers Q1.1 to Q1.4. Per-record evidence waits until a question stores derived items. |
| 2026-11-12 | Q1 `relatedLots` are found by a shared BIN only. Geosupport returns the billing BBL for condos, so a unit lot is not found by BIN; this is documented as a limit. Geosupport outcomes: exact, variant, ambiguous, not found, plus unavailable when the service cannot answer. | Verified on fixtures, including 185 Grand St (works) and the condo case (limit). |
| 2026-11-12 | Stage 5 setup. The ontology models only what the graph stores (graph-only scope). Reasoner: ROBOT 1.9.11 with HermiT, not ELK, because ELK misses functional data property violations. The check merges the TBox and each ABox file before reasoning, because ROBOT reads each file alone and treats undeclared properties as annotations. `address` has a union domain (lot or building); `hasBuilding` has no inverse. Pitfall scan: `make oops` sends the TBox only to OOPS!. | Stage 5 check (`make ontology`) passes 28/28. OOPS! found P11 (fixed) and P13 (left, minor). |
| 2026-11-12 | Stage 6 setup. Shapes are `shapes/qNN.ttl` (SHACL with `s2c:` graph names, compiled by shacl2cypher 0.3.0 in strict mode; every element needs an `s2c:` name). Coverage is `shapes/coverage.yaml`; seeded bad data is `tests/negative/qNN/cases.yaml`, run in rolled-back transactions by `scripts/check_shapes.py` (`make shapes`, part of `make graph`). Rules the compiler cannot express are covered by a named test (Q1: the two-counts rule, by `tests/q1_2`). No mapping files: `profiles/` and the loaders are the mapping. | Q1 `make shapes`: 46/46 (21 rules on the graph, coverage, 18 bad-data cases). Acceptance stays pending until the baseline dump is identified. |
| 2026-11-12 | Q2 registered owner. The registered owner contacts are those of type `CorporateOwner`, `IndividualOwner` or `JointOwner`; other contact types are not owners for Q2. All owner contacts of a registration are listed, none chosen. | Settles the open point on which HPD contact types count as registered owner. The three types are HPD's owner types; Agent, officers, site manager and others are different roles that must not be collapsed into the owner. |
| 2026-11-12 | Q2 graph model: `Registration` (registrationId), `HAS_REGISTRATION` from Building with `lastRegistered` and `registrationEnd`, `OwnerContact` (contactKey, contactType, name) and `HAS_OWNER_CONTACT` from Registration. Dates sit on the relationship because rows of one registration id can carry different dates; if the rows of a building and registration disagree, the date is absent. `registrationcontactid` is not unique in the snapshot, so contacts are keyed by registration, type and name and exact duplicates collapse. Blank names are absent. `data/sources.yaml` no longer lists it as the key. | Smallest graph that answers Q2.1 and Q2.2 and keeps role and date distinctions. Profiling showed the dates and contact ids cannot be taken at face value. |
| 2026-11-12 | Q2 stage 2. `profiles/q02.yaml` declares only what Q2 adds; `profiles/hpd_contacts.yaml` is a new source profile and `hpd_registrations.yaml` gains `registrationenddate`. `scripts/check_profiles.py` now merges every `profiles/qNN.yaml` and checks the shared graph as one set (a question may not redeclare another's property or relationship), declares relationship properties with types (including `date`), and compares enum values to a SKOS scheme after converting HPD's CamelCase spellings to the scheme's kebab-case IDs. `make profiles` passes 136/136. | The graph is shared across questions, so undeclared-element checks must see all questions' declarations. Relationship properties were needed because the registration dates belong to a building and registration pair. |
| 2026-11-12 | Q2 taxonomy: no hierarchy needed. Notes in `vocabulary/taxonomy-notes.md`. | A hierarchy exists only where an answer needs it. Whether a joint owner is a kind of individual owner is not settled, so no link is added. |
| 2026-11-12 | Q2 thesaurus: three related pairs, both directions (`registration-id`/`registration` identifier-of; `hpd-registered`/`registration` summary-of, new kind; `last-registered-date`/`registration-end-date` contrasts-with). External mappings: none sought. | Links only where the schema does not connect the concepts. `owner` would blur the HPD contact with deed grantee or portfolio owner. |
